The fixtures test the current policy snapshot: an email received before an SOP's effective date is still graded against the current SOP. Per [EVALUATION.md](../../docs/EVALUATION.md), a model from a different family reviews every email and its expected outcome; only disagreements, plus the 30-email anchor set, are read by a person. Until that review is done, treat the expected values as drafts.

All senders, organisations and lot or serial numbers are fictional. Senders on `.example` domains that match `customer_contacts.csv` are existing contacts; the others are unknown senders, which the product-documentation SOP allows.

## Schema (one JSON object per line)

| Field | Meaning |
| --- | --- |
| `email_id` | Stable ID: `E-DOC-nnn` / `E-TEC-nnn` / `E-QUO-nnn` / `E-CMP-nnn` / `E-ORD-nnn` / `E-INV-nnn` / `E-ONB-nnn` / `E-OTH-nnn` for single-category, `E-MIX-<categories>-nnn` for mixed |
| `received_at` | ISO timestamp |
| `from_name`, `from_email` | Sender |
| `subject`, `body` | The email as received; forwarded chains are kept in the body |
| `attachments` | Attachment names, if any |
| `persona` | Variety brief: formal, rushed, non-native, typos, forwarded chain, resend, prompt injection, urgent |
| `split` | `tune` or `held_out`. Held-out emails are never used while tuning prompts |
| `expected.labels` | Expected classification label set (exact-match grading, order-insensitive), assigned by [CLASSIFICATION_GUIDE.md](../../docs/CLASSIFICATION_GUIDE.md) |
| `expected.route` | Overall route: the most restrictive part route (`store_extraction` < `draft_for_approval` < `ask_for_clarification` < `escalate`), or `link_to_existing_case` for a duplicate email. `store_extraction` (supplier documents) means stored with no reply and no review |
| `expected.parts[]` | One entry per label, with the fields below |
| `parts[].route`, `parts[].owner` | Route for that part, and the owner when escalated |
| `parts[].send_documents` | `doc_id`s that must be attached. Documentation parts: exactly these. Technical parts: at least these; an extra attachment passes only if the reply cites it and it is current, shareable and for the same product (decided 2026-10-08) |
| `parts[].suggested_documents` | `doc_id`s that should be listed or offered, labelled as suggestions, but not presented as what was asked for |
| `parts[].must_not_send` | `doc_id`s whose attachment fails the case (an unsafe send) |
| `parts[].reply_must_state` | Case-specific points the reply or the review summary must contain, on top of the shared SOP rubric (EVALUATION.md); graded by the grounding judge |
| `parts[].passages` | Passages a person would consult (SOP section, or document and section), for the retrieval metrics |
| `parts[].quote` | Quotation parts only. `customer_id`, `account_status` (`active`, `on_hold`, `unknown_sender`), `payment_terms`, `postcode_used`, `postcode_source` (`email` or `account`), `zone`, `lines[]` (`sku`, `quantity` in units of sale, `unit_price`, `line_total`, `discount_rule`, `discount_percent`, `discount_amount`, `net_total`), `lines_are_options` (lines are alternatives shown for the customer to choose, not a basket), `goods_total`, `delivery_charge`, `vat`, `total`, `final`. Amounts are strings in pounds ex VAT, compared exactly. `final: false` means no total may be stated; `null` means no price is quoted at all |
| `parts[].suggested_alternatives` | Quotation parts: priced items offered as labelled suggestions (replacement, case pricing, nearest size), never as what was asked for |
| `parts[].pending_options` | Quotation parts: unit prices shown for a line still to be resolved (e.g. which version), alongside resolved lines in `quote.lines` |
| `parts[].prospect` | Quotation parts: `add` a row to `prospects.csv`, `update` its `last_seen`, or `null`. Emails are processed in `received_at` order |
| `parts[].payment_reminder_gbp`, `parts[].notify` | Quotation parts: the outstanding balance stated in the reminder (on-hold accounts), and teams told |
| `parts[].complaint` | Complaint parts only. `order_id` (found order, or null), `order_number_given`, `sender_matches_order` (null when no order found), `record_lines_for_reviewer` (the order's lines, for the reviewer only, never the customer's report), `delivery_date_source` (`record` or `customer`), `days_since_delivery`, `customer_stated_age` (approximate, never a date), `customer_quantity_estimate` (the customer's estimate, kept as words, never a confirmed quantity), `issues[]` (`type`, `product_name`: the catalogue name and version when the product is established, otherwise the customer's description; not the customer's exact words, which are not graded here; `sku` or null when not established by the email, `quantity_affected`, `window_days`, `window`), `window` (overall: `outside` if any issue is), `missing_info[]`, `safety`, `proposed_remedy` (proposal only), `customer_asks`, `flags[]`, `also_notify[]`. Order, sender and window values are computed from the records |
| `parts[].order_status` | Status, delivery-issue and change parts. `request` (`status` or `change`), `customer_reported_issue` (`missing_items`, `not_received`, `date_disputed` or null), `change` (`type`, `details`, for change requests), `orders[]` (`order_number_given`, `flags` (e.g. `outside_reporting_window`), `verification`: `verified`, `no_order_number`, `order_not_found`, `sender_does_not_match_order`, `not_authorised_for_orders`, `unknown_sender`; `reportable`; `record_for_reviewer`: order status, estimated dispatch, shipments with ID, lines carried, `original_estimated_delivery`, `current_expected_delivery` (the only date that may be reported; null for a delay without a revised date), `date_status` and delay reason, pending lines). The reply may state the record only when `reportable` is true |
| `parts[].order_request` | Order-placement parts. `customer_id`, `account_status`, `payment_terms`, `lines[]` (`customer_words`, `sku` or null, `quantity`, catalogue price, discount rule and net total), `goods_total_catalogue` (null when any line is unresolved or not orderable), `postcode_used`, `postcode_source`, `zone`, `customer_po`, `requested_date`, `quote_reference`, `missing_fields[]` (asked of the customer), `pending_attachment_review[]` (in an attached PO, read by the reviewer, not asked), `flags[]`, `notify[]`, `payment_reminder_gbp` |
| `parts[].invoice_request` | Customer invoice parts. `requests[]` (`given` number, `kind` `invoice` or `order`, `result`: `verified`, `no_identifier`, `not_found`, `several_invoices`, `not_invoiced_yet`, `sender_does_not_match`, `not_authorised_for_invoices`, `unknown_sender`; `invoices` resolved), `payment_question` (`balance`, `remittance_advice`, `payment_method`, `invoice_dispute`, `payment_status` or null; a payment-only email has no copy request), `identifier_conflict` (subject and body name different invoices), `record_for_reviewer`. `send_documents` holds the invoice numbers to attach |
| `parts[].supplier_documents[]` | Supplier parts, one entry per document. `file` (the mapped document; the attachment's display name may differ, so the harness loads this path), `document_type`, `extracted`, `extraction` (header fields and `lines[]`, exactly as printed; illegible fields null), `supplier_id`, `inserted` (false for a duplicate), `duplicate_of`, `needs_attention`, `flags[]` |
| `parts[].onboarding` | Onboarding parts. New accounts: `extracted` fields, `missing_fields[]`, `unclear_fields[]` (wrong format, unmatched postcode, a contact without email or role), `duplicate_of`, `similar_to`, `flags[]`, `record_action` (`created` or `none`), `record` (the customer row and contact rows to create, contacts including `role`, with IDs assigned in `received_at` order), `prospect_update`, `notify[]`. Changes: `change` (type and details), `verification`, `customer_id`. A held-out run must replay earlier created records first, as the IDs depend on them, and the quotation emails that add the prospects |
| `parts[].other` | Other parts. `subtype`, `reason_must_quote` (the words the summary must quote as the reason; null for an empty email, where the summary must say it is empty), `known_sender`, `language` (ISO code, or null when it cannot be identified), `flags[]` (e.g. `suspicious_link`, `data_request`, `prompt_injection`), `customer_reply` (always false) |
| `expected.combined_reply` | `mixed.jsonl` only: `single_reply` (always true) and `attachments`, the deduplicated union of the parts' `send_documents`. For the earlier mixed files the harness derives it the same way. Whether a ready part really waits for the others is a timing property the harness checks at run time; a fixture cannot show it |
| `expected.flags` | Pipeline flags, e.g. `prompt_injection` |
| `expected.duplicate_of` | For a resend, the email it duplicates |
| `trap_ids` | Case IDs from [TEST_TRAPS.md](../../docs/TEST_TRAPS.md) |
| `notes` | Why the expected outcome is what it is, where it is not obvious |

## Coverage

Every product-documentation trap P-01 to P-24 appears in at least one email. The variety brief is covered: formal, rushed, non-native and typo-ridden senders, a forwarded chain (E-DOC-036), a resend (E-DOC-037), and a prompt injection (E-DOC-035). Boundary cases that look technical but only ask for a document are E-DOC-004 and E-DOC-036. Mixed emails cover technical traps T-01 to T-06.

Other: traps X-01 to X-15 all appear. Every Other email escalates to Customer service with no reply; the five boundary cases route by their real category.

Onboarding: traps N-01 to N-15 all appear, with C-03, C-04, C-08, C-10, C-11 and D-06, D-08. Routes: 11 drafts (record created), 6 clarifications, 10 escalations (duplicates, not-served, injection, every account change), 1 duplicate email.

Mixed: traps M-01 to M-13 all appear. With the earlier mixed files there are 37 emails with more than one label, within the 30–40 planned. Rules the mixed set tests: one part per label; each part verified on its own terms; nothing sent until every part is ready; the most restrictive route; attachments deduplicated; within one email an onboarding part is applied first, so the email's other parts see the account it creates.

**Shared state across categories.** Customers, contacts and prospects form one state, built in `received_at` order across all files: a prospect added by a quotation is converted by a later onboarding email, and an account created by onboarding is used by a later quote (E-QUO-047). Generate in this order: orders, invoices, supplier documents, onboarding, quotations, the other single-category sets, then `generate_mixed_emails.py` last.

Invoices: traps I-01 to I-27 all appear, with C-01, C-03, C-04 and C-05. Routes: 6 drafts, 3 clarifications, 17 escalations (failed checks, payment questions, statements, the bank-details change, injections), 15 stored extractions, 1 duplicate email. The supplier register state is the seeded rows plus earlier insertions in `received_at` order; the generator replays that order, so E-INV-041 is a duplicate of what E-INV-021 stored, and E-INV-042 (no VAT number, matched by name) of what E-INV-040 stored. `duplicate_of: "inserted by E-INV-nnn"` names the email whose insertion it duplicates; the harness maps it to the register ID that insertion produced. In a held-out run, the tuning emails that insert are replayed first as unscored setup. RN-77344 and KSC-5203 are image-only scans (no text layer), so they need OCR or a vision model; their blotted values are the planted illegible fields.

Orders: traps O-01 to O-29 all appear, with C-01 to C-05, C-07, C-08 and C-12. Routes: 9 drafts (verified status), 3 clarifications, 33 escalations (delivery issues, failed verification, every order placement and change), 1 duplicate.

Complaints: traps R-01 to R-18 all appear. Every complaint part escalates (SOP §11): to Logistics for transit damage and wrong items, to Technical / quality review for quality defects, faults and returns.

Quotations: every quotation, discount and delivery trap Q-01 to Q-09 and D-01 to D-12 appears, plus customer traps C-03, C-04, C-05, C-07, C-08 and C-09. C-06 (on-hold account with no balance) needs a modified customer record and is left to a test fixture. Boundary cases that say "order" but ask a price are E-QUO-022 and E-QUO-023. Routes: 29 drafts, 12 clarifications, 5 escalations, 1 duplicate. Held-out emails are scored after replaying every email in `received_at` order, so prospect state set by tuning emails (E-QUO-018 before E-QUO-019) is present; the setup emails themselves are not scored in a held-out run.

Technical questions: every technical trap T-01 to T-15 appears in at least one single-category email (T-05 and T-06 in one each); T-16 is in `mixed_technical.jsonl`. Variety: formal, rushed, non-native, typo-ridden, urgent, a forwarded chain (E-TEC-036), a resend (E-TEC-037) and a prompt injection (E-TEC-035). Boundary cases that mention a document but ask what it says are E-TEC-026 and E-TEC-034, the counterparts of E-DOC-036 and E-DOC-004. Routes: 22 drafts, 16 escalations, 1 clarification (E-TEC-028), 1 duplicate. Passages are labelled at section level and checked against the document headings.
